# Lancer Nexus Gateway

## Administrative queries

Typed Protocol AdminQuery commands are relayed to Administration using private `Gateway:AdministrationBaseUrl` (HTTPS) and `Gateway:AdministrationApiKey`. External `POST /api/v1/admin/commands` checks the Gateway bearer token and current SQL session. Internal `POST /api/v1/game/admin/commands` checks the per-instance credential and admitted account/session/character lease. Transferred logins resolve the session from the committed Coordinator transfer before checking the active lease. Administration checks current SQL roles/scopes and durable audit for both transports. Routes have an independent 60/minute/source IP budget and no-store responses. See Administration's README for schema and configuration.

The Gateway is the public entry point for the Lancer Nexus MMO client. It authenticates accounts, creates sessions, assigns players to game instances and coordinates controlled transfers.

## Public market snapshot

`GET /api/v1/market/systems/{systemId}/goods` exposes one bounded page of the shared Coordinator market projection. It supports `pageSize` (1–500), `afterMarketId`, `afterGoodId` and `expectedSystemRevision`; continuation pages must pin the revision returned by the first page. A revision that is no longer available returns `409 Conflict`, so callers can restart pagination rather than combine inconsistent data. Responses include a short public cache lifetime and a page-specific `ETag`. Gateway uses its private HTTPS Coordinator connection and never returns the service credential. Reads are limited by `Gateway:MarketReadRateLimitPerMinute` (default 120 per source IP).

This endpoint returns reputation-neutral market rows. Personal quotes, the full goods catalog, trade booking and Coordinator reservation calls are not yet exposed by Gateway.

Authenticated `GET /api/v1/characters/{characterId}/faction-reputation` reads the character's saved `[Player] house` values from the latest Gateway-owned SaveGame snapshot. The bearer session must still be active in MySQL and the character must belong to that account. The response includes `reputationRevision`, which is the SaveGame snapshot revision; it does not claim to include simulation changes newer than the latest persisted snapshot. Missing faction entries use the game's neutral value `0`.

## Responsibilities

- E-mail and password login
- Password verification and account policy enforcement
- Short-lived signed access tokens and session management
- Instance assignment through the Coordinator
- Group and formation affinity during placement
- Transfer-ticket creation and validation
- Rate limiting, reconnect handling and public API health endpoints

The Gateway must not run authoritative world simulation. Persistent account and character data uses MySQL; chat and short-lived presence data may use Redis.

For permission mutations, instance snapshot synchronization and ACK trust boundaries, see [Administration's permission system guide](../Administration/docs/permission-system.md).

## Permission relay

Gateway relays permission snapshots and revision ACKs between authenticated game instances and Administration. Instance identity for ACKs comes from the instance-key authenticator, never from the request body. Public REST mutations require a valid Gateway session and are re-authorized by Administration; ingame mutations additionally require the active character lease. Keep the separate Administration service key private and never expose internal permission routes to clients.

Gateway also relays typed `AdminActionRequestV1` submissions at `POST /api/v1/admin/actions` and `/api/v1/game/admin/actions`. REST identity comes from the live token session; ingame identity comes from the authenticated instance plus active character lease, including committed-transfer session recovery. Gateway overwrites actor/source and resolves player targets from an active MySQL character lease plus the fresh Coordinator registry; move, transfer and teleport destinations must be live, ready and not draining. Client-provided target context and step-up status are ignored, and `StepUpVerified` remains false until a real attestation flow exists. A `202` means Administration durably queued the action, not that a game server executed it.

## Runtime

The service targets Linux and the current .NET runtime. Internal service communication uses the shared contracts from `Protocol` and private authenticated channels.

## Shared Protocol

The shared contracts are checked out in the `Protocol` submodule. Update it before every local build with:

```bash
git submodule update --init --remote --merge Protocol
```

CI recursively checks out the `Protocol` revision pinned by the Gateway repository before restoring and building.


The service exposes liveness, readiness and protocol-capability endpoints plus `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, protected `GET /api/v1/me`, protected `GET /api/v1/characters` and authenticated `POST /api/v1/placement/request` (with `/api/v1/placement` retained as a compatibility alias). Refresh tokens are separate opaque values, stored only as hashes and rotated atomically in MySQL. Placement requests require a valid Gateway access token whose `session_id` matches the request, then are forwarded to the Coordinator over its private HTTPS endpoint with a bearer key and idempotency key. `/api/v1/me` returns only non-sensitive token metadata and `/api/v1/characters` scopes results to the token account. The `SessionTokenCodec` signs short-lived access-token claims with HMAC-SHA256 and validates audience, expiry, nonce and key id; signing remains disabled until a protected key is configured. If token signing or the Coordinator URL/key is missing or invalid, the Gateway fails closed with `503`; it never makes a local placement decision.

`POST /api/v1/events/{eventId}/registrations` requires a valid access token, a currently active MySQL session and the character's active MySQL lease. Gateway derives account/session IDs from token claims and forwards the database lease version over HTTPS to Events using `Gateway:EventsBaseUrl` and a distinct `Gateway:EventsApiKey` of at least 32 UTF-8 bytes. Client supplied account, session and lease values are not accepted. The endpoint is rate limited by `Gateway:EventRegistrationRateLimitPerMinute` (default 10); missing Events configuration or an unavailable Events service returns `503`. The capability reports code support, not downstream availability. Event-server reservation, result export and return transfers remain separate work.

Access tokens expire after `Gateway:AccessTokenLifetimeMinutes` (default 10), capped by the session expiry. Sessions expire after five minutes without a successful refresh by default (`Gateway:SessionIdleTimeoutMinutes`, allowed range 1–1440), with a 24-hour absolute lifetime (`Gateway:SessionLifetimeHours`, allowed range 1–720). The client refreshes active sessions once per minute. Gateway revokes expired sessions every 30 seconds and clears their refresh-token hash; session rows remain for audit and transfer-journal integrity.

## MySQL schema

Gateway owns the identity/session/character schema and its lease fencing boundary. The forward-only migrations [`001_identity_and_leases.sql`](db/migrations/001_identity_and_leases.sql), [`002_refresh_token_rotation.sql`](db/migrations/002_refresh_token_rotation.sql), [`003_character_lease_transfers.sql`](db/migrations/003_character_lease_transfers.sql), [`004_character_transfer_snapshots.sql`](db/migrations/004_character_transfer_snapshots.sql), [`005_character_transfer_decisions.sql`](db/migrations/005_character_transfer_decisions.sql), [`006_character_save_snapshots.sql`](db/migrations/006_character_save_snapshots.sql), [`007_character_identity_allocation.sql`](db/migrations/007_character_identity_allocation.sql) and [`008_character_tombstones.sql`](db/migrations/008_character_tombstones.sql) create the account/session tables, transfer journals and encrypted snapshots, allocate Gateway-owned character IDs, and add history-preserving character tombstones. Apply them in order with the deployment migration runner after selecting the Gateway database; they are not executed automatically by the service and contain no credentials.

An authenticated game instance lists account characters at `POST /api/v1/game/characters/list` using the account and active session IDs. Gateway derives the calling instance from its key, validates the live MySQL session and returns only non-deleted Gateway character IDs and exact display names. `POST /api/v1/game/characters/delete` requires that same instance authentication and session check. It tombstones the account-owned character only when no live lease or staged transfer remains; retries return `duplicate`. Tombstones retain the unique display name and all lease, transfer-decision and snapshot rows for history. Deleted characters disappear from roster queries and cannot acquire or renew leases, write/read snapshots, or commit/abort transfers. `GET /api/v1/characters` also omits tombstones.

`POST /api/v1/game/characters/bootstrap` stores the initial SaveGame as encrypted revision 1 under the active account/session before a new character is selected. A retry never overwrites an existing snapshot. `POST /api/v1/game/characters/snapshot/preview` returns the account-owned latest snapshot for the character menu before lease acquisition; it requires both the caller's instance key and the active account/session and is read-only. Normal gameplay reads/writes still require the active character lease and fencing version.

An authenticated game instance can resolve a locally selected character by account, active session and exact display name at `POST /api/v1/game/characters/resolve-identity`. The operation is idempotent and returns the Gateway-owned `character_id` plus a short-lived signed lease ticket bound to that character and the authenticated instance; LLServer immediately submits the ticket to lease acquisition. A name already owned by another account or a tombstoned character conflicts. LLServer must retain this Gateway ID separately from its local SQLite row ID and use it for leases, snapshots and transfer authority. LLServer consumes the authoritative roster and routes deletion through Gateway before removing its local compatibility cache row. New clustered characters register their initial SaveGame as revision 1 before appearing in the character menu; pre-selection previews are account/session-bound and read-only. A legacy character without a snapshot can only be shown by an instance that still has its local SQLite row; absent state is omitted rather than recreated.

Instances use `POST /api/v1/game/characters/snapshot/write` and `/read` with their instance key plus the active lease token and `lease_version`. Gateway validates the live SQL session, account, instance, token hash and fencing version while locking the character row. Writes advance one revision at a time; identical retries at the current revision are idempotent, while stale fences or gaps are rejected. The opaque SaveGame payload is capped at 16 MiB, SHA-256 checked, and encrypted with AES-256-GCM. Snapshot encryption reuses `Gateway:TransferSnapshotCurrentKeyId` and `Gateway:TransferSnapshotKeys:<key-id>`; retain old keys while snapshots encrypted with those IDs remain. Existing characters have no durable SaveGame until the game instance writes revision 1. These endpoints are a persistence boundary; LLServer still needs to route its normal load/save lifecycle through them before character persistence is fully integrated.

Game instances renew leases at `POST /api/v1/game/renew-character-lease` using the same lease token and `lease_version`. Renewal extends `valid_until_utc` without incrementing the fence and succeeds only for the authenticated current instance, active account/session, unexpired lease and matching token hash. A missed expiry cannot be revived by renewal. Acquisition rejects a conflicting lease while its owner session remains active; after lease expiry or owner-session expiry/revocation, a valid new session can take over under the character-row lock, and every takeover increments the fence. The lease lifetime is controlled by `Gateway:CharacterLeaseLifetimeSeconds` (60–86400 seconds, default 900).

The Gateway uses `MySqlConnector` for account reads and session creation through `IAccountRepository`. `POST /api/v1/auth/login` verifies bcrypt hashes, persists the session nonce hash and returns a signed short-lived token. Redis is configured through `Gateway:RedisEndpoint` and is checked with a bounded PING during readiness; it remains transient infrastructure and never replaces MySQL authority. With an empty `ConnectionStrings:Gateway` setting the service registers fail-closed repositories and does not provide demo or in-memory accounts; login and transfer persistence return `503` until the database and signing keys are configured.

The repository reads a currently valid character lease only when character ownership, active account, active session and session-to-lease ownership all match. After character selection, an authenticated game instance can call `POST /api/v1/game/acquire-character-lease` with the admitted join ticket, selected character ID and a proposed 32-byte lease token. Gateway derives account, session and target instance from the signed ticket and instance key, checks the selected character against any ticket binding, rechecks active SQL session/account/character ownership, then acquires or renews the lease under a character-row transaction. Initial ownership starts at fencing version 1; an identical retry returns the same version, another active owner is rejected, and expiry takeover increments the version. Only the token hash is stored. The endpoint does not make LLServer use the lease yet, and expiry/recovery behavior still needs end-to-end verification.

The transactional `CommitCharacterLeaseTransferAsync` primitive locks the same character row, checks active account/session ownership, requires the expected live lease version and source instance, increments the fencing version, rotates the target lease-token hash and records the transfer ID in the same MySQL transaction. The authenticated target-acceptance route invokes this transaction after Coordinator records `TargetAccepted`; matching retries are idempotent and a reused transfer ID with different inputs is rejected. Snapshot delivery and GameServer lease enforcement remain separate work.

`CoordinatorTransferClient` wraps the Coordinator's authenticated internal prepare, lookup, state-advance, commit and abort endpoints. It applies the configured HTTPS endpoint, bearer API key and timeout, and rejects replies for a different transfer ID. The Gateway start/reservation step is public to authenticated clients; internal lifecycle transitions remain service-to-service.

The shared Protocol defines `TransferTicketClaims` with explicit MessagePack keys for transfer, session, account, character, source and target, target system, current lease version, expiry, nonce, audience and key ID. Gateway's `TransferTicketCodec` signs these claims with a separate HMAC key (`Gateway:TransferTicketSigningKey`) and caps ticket lifetime at two minutes. Target verification checks the active Coordinator transfer and atomically consumes a distinct Redis nonce.

`POST /api/v1/transfers/start` is now the authenticated reservation entry point. It binds the request to the bearer session, obtains the live source instance and fencing version from MySQL, asks Coordinator to reserve the specified target with the transfer ID and idempotency key, then returns the Coordinator endpoint and a signed ticket carrying the database-derived source/version. Set `Gateway:TransferRateLimitPerMinute` to tune its per-IP limit. An unavailable lease returns `409`, Coordinator/configuration failures return `503`, and malformed Coordinator replies return `502`.

After LLServer freezes the source, its authenticated instance uploads the raw `.fl` body to `POST /api/v1/game/freeze-transfer/{transferId}` with `X-Lancer-Nexus-Lease-Version` set to the lease version returned at transfer preparation. Gateway rechecks that exact active MySQL lease still belongs to the source, caps snapshots at 16 MiB, encrypts them with AES-256-GCM using the transfer ID as associated data, durably stages them in MySQL, and only then advances the Coordinator transfer from `Prepared` to `SourceFrozen`. Upload retries with identical metadata and content are idempotent; reusing an ID with different content is rejected. Configure `Gateway:TransferSnapshotCurrentKeyId` and `Gateway:TransferSnapshotKeys:<key-id>` with a protected base64-encoded 32-byte key. Retain old key IDs while matching snapshot rows exist; rotate the current ID only after adding the new key to the key ring. The target instance can fetch the snapshot as `application/octet-stream` from `GET /api/v1/game/transfers/{transferId}/snapshot` after `SourceFrozen`; Gateway checks its per-instance key and the Coordinator target binding. Target-side ticket verification and MySQL/Coordinator target-acceptance are available. LLServer has HTTP helpers for upload and fetch but does not yet import the returned save into its local character database, and lease enforcement remains pending; jump-gate travel is not end-to-end ready.

Successful placement responses contain a short-lived, single-use `JoinTicket` bound to the session, account, optional character, target instance/system and endpoint. The ticket uses the separate `Gateway:JoinTicketSigningKey`; Gateway atomically consumes its nonce in Redis at `POST /api/v1/game/verify-ticket`, and the target game server must call that endpoint before accepting a client connection. It is not a replacement for the MySQL lease.

Transfer starts return a short-lived `TransferTicket` bound to the session, character, source and target instances, target system and current lease version. Configure a distinct bearer secret of at least 32 characters for each instance under `Gateway:GameInstanceKeys:<instance-id>`; these secrets identify the caller and must be delivered through the protected deployment secret store. Game instances must call all transfer API routes over HTTPS. The target game server posts the ticket to `POST /api/v1/game/verify-transfer-ticket` with its instance ID and per-instance bearer. Gateway derives the caller identity from that key, checks the requested ID, validates the ticket binding, confirms the Coordinator transfer is `SourceFrozen`, and atomically consumes a separate Redis nonce before returning admission claims.

After loading and preparing the transferred character snapshot, the authenticated target posts the same ticket plus a fresh 32-byte base64url `TargetLeaseToken` to `POST /api/v1/game/accept-transfer`. Gateway validates the target identity and Coordinator transfer, advances it to `TargetAccepted`, atomically switches the MySQL lease and increments `lease_version`, then confirms `Committed` with Coordinator. Matching retries with the same token finish a partially completed Coordinator commit; changing the token for a used transfer ID is rejected. Once Coordinator has recorded `SourceFrozen`, the target can use the signed ticket for lifecycle recovery after its two-minute expiry; the authenticated instance binding and persisted active transfer state are still required, and Redis retains the nonce key for 24 hours after ticket expiry. The target receives the committed lease version and already retains its proposed token. Configure `Gateway:CharacterLeaseLifetimeSeconds` between 60 and 86400 (default 900).

Source and target instances can poll `GET /api/v1/game/transfers/{transferId}` with their per-instance bearer. Gateway exposes status only to the two bound instances and disables response caching. Commit status requires the durable `character_lease_transfers` record with matching transfer, session, character, source, target and incremented lease version. If SQL committed but the Coordinator acknowledgement was lost, the response reports `Committed` and the SQL version. Coordinator commit/release claims without SQL proof, inconsistent bindings or a Coordinator abort conflicting with a SQL commit fail closed with HTTP 502; unavailable persistence returns 503. Historical commit proof remains valid after session expiry or a later transfer; it proves that handoff occurred, and does not grant a current active character lease.

After local player teardown, the source calls `POST /api/v1/game/release-transfer`. Gateway verifies the source and SQL commit, idempotently finishes the Coordinator commit acknowledgement, advances `SourceReleased` and deletes the staged character snapshot. Missing or conflicting SQL proof prevents both source release and snapshot deletion. This improves recovery of the character commit window; it does not yet enforce joint mission NPC commit/abort at the Coordinator's NPC phase endpoint.

The character commit integration test runs in CI against an ephemeral MySQL 8.0 service. Locally, set `LANCER_NEXUS_GATEWAY_TEST_MYSQL` to an isolated test server to enable it. The test creates and drops its own uniquely named database, applies migrations 001, 003 and 005, executes a fenced lease handoff and duplicate retry, recreates the repository, and verifies historical commit reads after another handoff and session/lease expiry. It also verifies migration backfill of existing commit records, durable abort replay, rejection of commit after abort and abort after commit, stale fence rejection, and twelve concurrent commit/abort races on separate SQL connections. No account or world data in the configured database is modified.

### Durable character transfer decisions

Apply [`005_character_transfer_decisions.sql`](db/migrations/005_character_transfer_decisions.sql) after the earlier migrations, with Gateway transfer writers stopped. It adds a permanent decision table and copies existing character commit journal entries into it. New Gateway lease commits require this migration and write the decision, lease switch and commit journal atomically. The repository's explicit abort operation takes the same character-row lock, verifies the unchanged source lease fence and stores an immutable abort decision. Matching retries survive restart; later commit of that transfer ID is rejected. Aborting an already committed transfer is rejected with its historical committed lease version. The shared primary key prevents both decisions from being stored for the same transfer, including conflicting identity bindings.

An abort decision prevents a future character commit; it does not restore an expired session or grant simulation authority. Status exposes the durable abort even before its Coordinator acknowledgement, allowing frozen-source recovery to retry safely.

`POST /internal/v1/npc-mission-authority` is the private HTTPS Coordinator boundary using the Protocol `NpcMissionAuthorityRequestV1` and `NpcMissionAuthorityResultV1` contracts. Configure `Gateway:NpcMissionAuthorityApiKey` with a dedicated secret of at least 32 UTF-8 bytes. The route rejects HTTP and any credential recognized as a game-instance key, returns 503 when unconfigured or authority is unavailable, and disables response caching. Requests bind the shared character/mission transfer ID, source, target and target system to the Coordinator character request. Commit requires the matching permanent SQL decision and commit journal; abort writes the permanent SQL veto against the staged character snapshot fence, then idempotently acknowledges character abort with Coordinator. A pre-freeze abort can use the unchanged active source lease when no character snapshot exists. A missing frozen snapshot never authorizes rollback. Repeated decisions survive lost responses; their transfer identity cannot be reused.

Coordinator enforces this decision before mission NPC commit, abort and terminal snapshot restoration. Autonomous population transfers use their existing NPC lease transaction. This is a recoverable handoff across the two service schemas, not one cross-service SQL transaction. Full live mission handoff and process-failure acceptance still require runtime verification.

Login and placement use separate per-client-IP fixed-window limits from `Gateway:LoginRateLimitPerMinute` and `Gateway:PlacementRateLimitPerMinute`; rejected requests receive HTTP `429` before account or Coordinator work starts.

## Client version handshake

Before login, clients POST the shared `ClientVersionHello` contract to `/api/v1/client/version`. The Gateway compares protocol, data manifest, channel, platform and minimum/latest client versions from `Gateway:ClientProtocolVersion`, `Gateway:RequiredDataManifestId`, `Gateway:ClientChannel`, `Gateway:MinimumClientVersion` and `Gateway:LatestClientVersion`. Supported and recommended versions receive a five-minute, domain-separated HMAC handshake token. The client submits it as `handshakeToken` in the login JSON; missing, invalid or expired proof receives HTTP 428 before password verification. Required updates and unsupported protocols receive no proof. This proof establishes compatibility only and grants no account or placement rights. The Gateway does not supply a download URL; the local updater uses its configured signed manifest source.

The proof is bound to the reported version, protocol, data manifest, platform and channel. Those fields are checked again at login, so a policy change can invalidate a proof that was issued minutes earlier.

`/health/live` is process liveness only. `/health/ready` fails closed until the signing key, Coordinator API key/URL, Gateway MySQL connection and Redis endpoint are configured and both `SELECT 1` and Redis `PING` succeed.

Transfer mutation and snapshot endpoints apply `Gateway:TransferRateLimitPerMinute` separately per client IP, HTTP method and matched route template. Transfer IDs do not create new buckets. This keeps every step rate limited while allowing consecutive handoffs without their different steps consuming one shared budget. Status polling retains its separate limit.

Character SaveGame read/write endpoints use `Gateway:CharacterSnapshotRateLimitPerMinute`, partitioned by authenticated game instance. The default is 600 requests per instance per minute, which accommodates the eight-group baseline's 200-player instances, periodic checkpoints and explicit saves with room for retries. LLServer staggers its one-minute checkpoints across character IDs.

For the eight-group Nexus baseline, set `Gateway:GameInstanceKeysFile` to the mode-0600 JSON key map generated by Scripts. It supplements configured keys and binds private per-instance credentials to IDs such as `br-01` and `mixed-01`. Reloading requires a Gateway restart.
